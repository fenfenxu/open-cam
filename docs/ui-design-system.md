# open-cam 控制台设计规范

> 执行规则以仓库根目录 design.md 为准。本文件提供完整的设计理由、视觉基础、领域原则和业界参考；两者不一致时，先更新根目录规范，再同步本文件。

版本：0.1（待确认）  
适用范围：`web/` 控制台，以及所有面向用户的页面、组件、文案和交互。  
产品类型：本地视频监控分析与事件处置控制台。

这不是某个页面的视觉稿，而是后续新增页面、重做组件和评审交互时的共同判断标准。当前项目已有的实现可以继续保留，但新增内容必须遵守本规范；如果现有实现与本规范冲突，以本规范为准，按优先级逐步收敛。

## 0. 先确认这 10 条不可妥协的原则

1. **用户不需要猜。** 任何选中值、状态、图标和颜色，在脱离上下文时仍应能被理解。
2. **先让人看懂，再让人操作。** 页面先呈现任务目标、数据状态和下一步动作，装饰性视觉不得抢占监控信息。
3. **一件事只有一种表达。** 同一个概念的名称、颜色、图标、状态和动作不能在不同页面随意变化。
4. **状态和动作分开。** “已确认”是状态，“确认”是动作；“误报”是判定，“忽略”是处置动作。
5. **默认安全、操作可逆。** 删除、忽略、停止摄像头、部署模型等不可逆或高风险动作必须明确后果并允许取消。
6. **AI 结论不是事实。** 大模型判定、置信度、理由和人工判定必须分层展示，不能把模型输出伪装成人工事实。
7. **颜色不是唯一信息。** 红色、绿色、黄色只能强化文字、图标或结构，不能单独承担“异常 / 成功 / 待处理”的含义。
8. **密度服务于值班效率。** 允许信息密集，但必须有清晰层级、稳定对齐和足够的点击空间。
9. **反馈要告诉用户下一步。** 错误不能只说“请求失败”；成功也不能只闪一个没有上下文的提示。
10. **规范优先于局部修补。** 页面内不能重新发明按钮、筛选器、状态徽标或提示样式，优先扩展公共组件和语义 token。

## 1. 产品体验定位

open-cam 是一个“值班与处置”产品，不是展示型大屏，也不是普通 CRUD 后台。用户通常在以下任务之间切换：

- 判断当前有没有需要处理的事件；
- 快速定位事件来源、时间、素材和规则；
- 判断大模型结果是否可信；
- 完成确认、指派、备注、忽略、处置和通知重发；
- 配置摄像头、规则、模型和方案；
- 在本地资源有限、网络不稳定或模型不可用时继续工作。

因此，设计优先级固定为：

**可理解性 > 可扫描性 > 可操作性 > 信息密度 > 装饰性。**

## 2. 视觉基础

### 2.1 视觉性格

- 基础气质：克制、可靠、专业、偏中性。
- 页面主体以中性灰度为主，强调色只用于主要动作、当前选择和需要注意的状态。
- 不使用大面积渐变、强装饰插画、无意义的发光效果或会干扰视频证据阅读的背景。
- 监控素材优先保持真实比例和真实颜色；任何叠加层都必须能被关闭或不遮挡关键证据。

### 2.2 颜色 token

组件只能引用语义 token，不直接在页面里写十六进制颜色或随意写新的 `oklch` 值。当前项目已有 `--background`、`--foreground`、`--muted`、`--border`、`--primary`、`--destructive`、侧边栏和图表 token，后续继续沿用这一层抽象。

| Token 角色 | 用途 | 规则 |
| --- | --- | --- |
| `background` | 页面底色 | 保持最低视觉权重 |
| `card` / `popover` | 卡片、弹层、下拉菜单 | 与所在层有清晰边界 |
| `foreground` | 主标题、正文、关键数据 | 默认最高文字对比度 |
| `muted-foreground` | 描述、辅助信息、时间 | 不用于唯一传达状态或重要操作 |
| `border` / `input` | 控件边界、分隔线 | 不靠过浅边界组织复杂布局 |
| `primary` | 主要动作、当前选择、主链接 | 一个区域只保留一个主要动作 |
| `success` | 成功、已处置、运行正常 | 必须同时有文字或图标 |
| `warning` | 不确定、即将影响、配置不完整 | 必须说明原因或建议动作 |
| `destructive` | 失败、危险、不可逆动作 | 不把所有错误都渲染成红色 |
| `info` | 解释、提示、系统说明 | 不打断当前任务 |
| `focus` | 键盘焦点 | 在浅色和深色主题中都必须可见 |

项目需要补充 `success`、`warning`、`info` 的语义变量，并为浅色 / 深色主题分别校验。颜色对比基线采用 WCAG 2.2 AA：普通文字至少 4.5:1，大号文字至少 3:1，控件边界和状态指示至少 3:1；不能只依赖颜色区分状态。[WCAG 2.2](https://www.w3.org/TR/WCAG22/)、[Carbon Color](https://carbondesignsystem.com/guidelines/color/usage/)

### 2.3 字体与文字层级

当前使用 Geist Variable。中文回退字体必须明确，建议顺序为：

`Geist Variable` → `ui-sans-serif` → `system-ui` → `PingFang SC` → `Microsoft YaHei` → `sans-serif`。

建议层级：

| 层级 | 用途 | 建议 |
| --- | --- | --- |
| 页面标题 | 页面主任务 | 24px / 32px，medium |
| 区块标题 | 卡片、抽屉、模块标题 | 16px / 24px，medium |
| 正文 | 表单、说明、常规数据 | 14px / 20px |
| 辅助信息 | 时间、来源、帮助说明 | 12–13px / 18px |
| 表格数据 | 高密度记录 | 13–14px / 20px |
| 数字指标 | 仪表盘核心数字 | 24–32px，根据空间调整 |

规则：

- 用户可读内容全部使用中文；技术缩写可以保留，但第一次出现时给出中文含义。
- 不用全大写、不用标题式大小写、不用靠加粗制造过多层级。
- 一段说明尽量控制在两句内；如果需要更长解释，拆成帮助区、详情页或文档。
- 字体缩放到 200% 时不丢失内容或功能。

### 2.4 间距、圆角和层级

- 以 4px 为基础间距单位，优先使用 `4 / 8 / 12 / 16 / 24 / 32`。
- 控件高度：紧凑控件 28px，常规控件 32px，主要操作 36px；触控和图标目标优先达到 32px。
- 控件圆角统一使用现有 `--radius` 体系；常规输入、按钮、下拉约 8px，卡片约 10–12px，禁止页面内随意混用圆角。
- 阴影只用于弹层、抽屉、浮动反馈；页面卡片优先用背景层次和边界，不堆叠阴影。
- 分隔线只表达结构，不把每个区域都切成孤立盒子。

### 2.5 图标和动效

- 统一使用 Lucide 线性图标；常规图标 16px，区块图标 20px，图标按钮必须有 `aria-label` 和 tooltip/title。
- 图标不能单独承担“删除、停止、忽略”等高风险动作的含义，必须配文字或明确的可访问名称。
- 动效默认 150–200ms，用于状态变化、抽屉、菜单和按钮反馈；不使用持续闪烁来表示普通状态。
- 支持 `prefers-reduced-motion`，减少或关闭非必要动画。

## 3. 页面骨架

每个页面优先遵守以下结构：

1. **页面标题区**：标题、面向任务的简短说明、页面级动作。
2. **工具栏**：搜索、筛选、视图设置、批量动作；控件按用户频率排序。
3. **主内容区**：表格、卡片、视频墙、画布或表单。
4. **反馈区**：加载、空状态、错误、成功和数据更新时间。
5. **详情层**：抽屉适合查看和处置上下文；模态框适合需要用户明确决策的短任务。

页面标题和主内容应保持左边缘对齐。主内容区以可读性为上限；事件表、视频墙等高密度内容可以使用更宽布局，但不能为了填满屏幕而拉伸文字和控件。

侧边栏继续采用“分组 + 当前页面高亮 + 可折叠”模式：

- 当前页面必须同时有视觉高亮和 `aria-current="page"`；
- 折叠后图标必须有 tooltip/title；
- 导航文案使用产品词汇，不显示内部路由名；
- 侧边栏、底部开发提示和浮层不能遮挡键盘焦点或主要操作。

## 4. 核心组件规范

### 4.1 按钮

| 类型 | 用途 | 规则 |
| --- | --- | --- |
| Primary | 当前区域最重要的提交 / 创建 / 应用动作 | 同一区域最多一个 |
| Outline | 次要但明确的动作 | 不与 Primary 竞争 |
| Ghost | 重置、收起、辅助操作 | 不用于关键提交 |
| Destructive | 删除、停止、忽略等危险动作 | 文字说明后果，必要时二次确认 |
| Link | 页面内导航、文档链接 | 文案必须说明目的 |
| Icon-only | 高频且明确的工具动作 | 必须有可访问名称和 tooltip |

按钮文案使用“动词 + 对象”：`添加摄像头`、`保存规则`、`确认事件`、`重置筛选`。避免 `确定`、`提交`、`操作` 这种缺少对象的词。

### 4.2 表单、输入和选择

- 每个输入控件必须有持久可见 Label；placeholder 只能补充示例，不能代替 Label。
- 帮助文案解释“填什么、为什么填、限制是什么”；错误文案说明“哪里错、怎么改”。
- 必填项在 Label 附近统一表达，不靠红色边框猜测。
- 表单提交失败后保留用户输入，并把焦点或错误提示带到第一个问题字段。
- 选择项显示用户语言，不显示内部枚举、数据库 ID 或 `__all__`。

#### 横向筛选的强制规则

没有外置 Label 的工具栏筛选必须使用“字段名：选中值”，例如：

- `摄像头：[1] 演示摄像头`
- `类型：徘徊逗留`
- `状态：已确认`
- `VLM 判定：误报`

当前项目统一使用 `LabeledSelect`。筛选条还必须具备：

- 一键 `重置筛选`；
- 无条件时按钮仍然可见但禁用；
- 多个条件同时存在时，不要求用户逐个清除；
- 条件变化后明确保留当前条件，刷新不应悄悄重置；
- 移动端允许换行，但字段名不能被截断。

具体规则见 [ui-filter-guidelines.md](./ui-filter-guidelines.md)。

### 4.3 状态徽标

状态徽标只表达状态，不承担按钮功能。建议固定以下维度：

| 维度 | 示例 | 说明 |
| --- | --- | --- |
| 事件处置状态 | 待处理、已确认、已处置、已忽略 | 人的工作流状态 |
| 大模型复核状态 | 待复核、已完成、已跳过、复核失败 | 系统处理状态 |
| 大模型判定 | 已确认、误报、不确定 | 模型输出，不等于人工结论 |
| 摄像头状态 | 运行中、已停止、异常 | 设备 / 流状态 |
| 训练状态 | 草稿、训练中、已完成、失败 | 训练任务状态 |

禁止把多个维度合并成一个难以解释的徽标，也禁止直接把英文内部值显示给用户。高风险或高影响状态使用“图标 + 文案”，不能只用颜色。

### 4.4 表格

表格上方放标题、说明和全局工具栏；筛选、搜索和视图设置紧邻表格，不藏在无上下文的菜单中。Carbon 将数据表工具栏定义为放置主要按钮、搜索、筛选、显示设置和其他工具的位置；Material 也建议把影响表格数据的筛选和分页放在表格附近。[Carbon Data table](https://carbondesignsystem.com/components/data-table/usage/)、[Material Data tables](https://m2.material.io/design/components/data-tables.html)

规范：

- 列名短而明确，优先 1–4 个中文词；需要解释时放帮助或 tooltip，不把整句塞进表头。
- 时间、状态、来源和主对象保持稳定列顺序；高频识别字段优先靠左。
- 行可点击时整行保持一致的 hover / focus 反馈，并且键盘用户有等价入口。
- 行内动作少于 3 个时可直接展示，更多动作进入操作菜单；危险动作不要藏到用户难以发现的位置。
- 数据加载优先使用与表格结构相似的 skeleton；不可避免的长耗时显示“正在加载”及必要的取消或重试。
- 空状态必须区分“没有数据”“筛选后没有结果”“加载失败”；筛选后为空时优先给 `重置筛选`。
- 数据太宽时允许横向滚动，但不能把列压缩到不可读；移动端优先展示关键列并提供详情入口。
- 表格分页位于表格底部；过滤和排序状态需要能被用户看见。

### 4.5 视频、快照和画布

- 快照和视频保持原始宽高比，默认 `object-contain`，不为填满卡片而裁掉证据。
- 所有素材有可理解的替代文案、时间、摄像头和事件关联；素材加载失败要说明格式或来源问题。
- 证据层叠加框、区域、多边形和计数线要有图例或说明；不要用同一种颜色表示“检测框、区域、告警等级”。
- 播放、暂停、静音、全屏等控件优先使用浏览器原生能力；自定义控件必须支持键盘和可访问名称。
- 画布操作提供清晰的当前模式、撤销 / 重做或取消入口；危险操作不能只靠拖拽完成。

### 4.6 抽屉、模态框和确认

- 抽屉用于“保留列表上下文的查看与处置”，不适合塞入完整配置向导。
- 模态框用于短、明确、需要用户决策的任务；删除、停止、覆盖、部署等动作必须说明影响范围。
- 打开后焦点进入层内，`Escape` 可关闭，关闭后焦点回到触发点；层内 Tab 循环不能跑到背景页面。[WAI-ARIA Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- 弹层必须有标题；复杂内容不要为了读屏而强行拼成一段无结构描述。
- 详情抽屉的标题区固定保留关闭、展开 / 收回等操作；内容区按“结论 → 证据 → 详情 → 历史 → 动作”排列。

### 4.7 Toast、横幅和错误反馈

通知分四类：

| 类型 | 用途 | 生命周期 |
| --- | --- | --- |
| Inline | 当前页面或当前任务的状态 | 保留在上下文中 |
| Toast | 短暂的成功、普通提示 | 自动消失，但不能承载唯一结果 |
| Actionable | 需要用户下一步处理 | 保留到处理或关闭 |
| Callout / Banner | 页面进入时就重要的指导或系统状态 | 通常不自动消失 |

Carbon 也将通知分为 toast、inline、actionable 和 callout，并强调通知应少量使用、短而明确、错误消息必须包含解决下一步。[Carbon Notification](https://carbondesignsystem.com/components/notification/usage/)

规则：

- 成功：`规则已保存`，必要时附 `查看规则`。
- 失败：`规则保存失败。请检查区域是否闭合后重试。`
- 网络 / 服务问题：说明是否已保存、是否可以重试、是否需要检查后端。
- 不让重要错误只存在于会自动消失的 toast 中；需要用户处理的问题放 inline 或 banner。
- 动态反馈使用适当的 `role="status"` / `role="alert"`，不要抢夺用户焦点；WAI-ARIA Alert Pattern 明确要求 alert 不应改变键盘焦点，也不应消失得快到用户无法读完。[WAI-ARIA Alert Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alert/)

## 5. open-cam 的领域规范

### 5.1 事件信息的四层模型

事件列表和详情始终按以下顺序理解：

1. **发生了什么**：规则类型、时间、摄像头、素材；
2. **系统怎么看**：检测置信度、大模型状态和判定、判定理由；
3. **人怎么判断**：人工判定、负责人、备注；
4. **事情到哪一步**：待处理、已确认、已处置、已忽略，以及操作历史。

“观察记录”和“待办告警”是业务语义，不只是筛选条件：

- 观察记录默认进入客流 / 统计视图，不进入待办；
- 待办告警必须有处置状态机；
- 页面标题和说明要明确当前看到的是“待办”还是“观察记录”。

### 5.2 AI 可信度表达

- 对模型输出统一使用“大模型复核 / 大模型判定”等用户可理解的中文；技术页面可补充 `VLM`。
- 模型没有运行、跳过、失败、看不清时，显示具体状态，不伪装成“无结论”或成功。
- “已确认”如果来自模型，必须明确是“大模型判定：已确认”；“属实”只用于人工判定。
- 置信度必须带单位或解释，例如百分比、区间或“高 / 中 / 低”，禁止只展示一个没有语境的数字。
- 模型理由和快照是证据，不是替代人工处置的命令；高风险动作始终由用户确认。

### 5.3 摄像头与系统健康

- 摄像头名称是主识别信息，编号用于消歧，不替代名称。
- 运行中、已停止、异常必须同时显示状态和影响；异常要提供查看日志、重连或重启路径。
- 设备、检测器、模型、VLM 配置的内部枚举统一转成中文展示。
- 本地服务不可用时，页面显示“控制台与后端连接中断”等明确状态，不把空表格误认为没有数据。

## 6. 响应式规范

### 桌面端

- 保留侧边导航和宽表格；事件详情使用右侧抽屉。
- 页面级动作靠近标题，表格级动作靠近表格。
- 筛选条允许换行，但同一维度的标签和取值不能分离。

### 平板端

- 侧边栏可折叠；筛选控件分两行排列。
- 表格保留横向滚动，冻结最关键的识别列或提供详情入口。

### 手机端

- 主导航折叠为可展开菜单；抽屉变为全屏层。
- 筛选条改为“筛选”入口 + 已选条件摘要，不能把 5–6 个控件硬挤在一行。
- 详情按“结论、证据、动作”分段；非关键字段收进折叠区域。
- 触控目标至少 24×24 CSS px，项目默认优先 32px，并给相邻小目标留出间距。[WCAG 2.2 Target Size](https://www.w3.org/TR/WCAG22/#target-size-minimum)

## 7. 无障碍基线

目标：WCAG 2.2 AA；组件交互遵守 WAI-ARIA APG。

必须做到：

- `html lang="zh-CN"`；
- 所有可操作元素可用键盘到达；焦点可见，且不被固定 banner、抽屉或浮层完全遮挡；
- 普通文本对比度至少 4.5:1，大号文本至少 3:1，控件和焦点边界至少 3:1；
- 交互目标至少 24×24 CSS px，项目常规控件优先 32px；
- Select / combobox 有独立的可访问名称和当前值，键盘支持打开、上下选择、Escape 关闭；[WAI-ARIA Combobox Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)
- 对话框有标题、焦点管理、Escape 关闭和明确的关闭按钮；
- 动态成功、状态、错误消息能被辅助技术感知，但不无故抢焦点；
- 颜色、图标、文字和结构至少使用其中两种表达重要状态；
- 支持 200% 文字缩放和 `prefers-reduced-motion`。

## 8. 文案规范

### 语气

- 简洁、直接、面向行动，不使用冗余客套语。
- 用用户能理解的中文，不把后端异常、数据库字段名、枚举值直接抛给用户。
- 说明原因时先说结果，再说原因和下一步。

### 动作命名

| 场景 | 推荐 | 避免 |
| --- | --- | --- |
| 保存 | 保存规则、保存设置 | 提交、确定 |
| 新建 | 添加摄像头、创建任务 | 新增、创建 |
| 处置 | 确认事件、标记误报、完成处置 | 处理、操作 |
| 清理条件 | 重置筛选 | 清空、刷新 |
| 重试 | 重新加载、重试推送 | 再来一次 |
| 危险动作 | 停止摄像头、删除规则 | 确定 |

### 术语表

| 概念 | 统一用词 | 不混用 |
| --- | --- | --- |
| 监控来源 | 摄像头 | 相机、设备（除非指硬件） |
| 可被人处置的事件 | 待办告警 | 告警、事件、任务混作同义词 |
| 仅记录不处置 | 观察记录 | 普通事件、日志 |
| 大模型复核结果 | 大模型判定 | AI 结论、VLM 结论混用 |
| 人工确认结果 | 人工判定 | 已确认（不说明来源） |
| 证据图像 | 快照 | 截图、照片混用 |
| 侧滑详情 | 详情抽屉 | 侧边栏、弹窗混用 |

## 9. 设计与开发验收清单

每个新页面或重大改动至少检查：

- [ ] 页面标题是否说明当前任务，而不是只显示模块名？
- [ ] 首屏是否能看出数据正在加载、为空、失败还是有结果？
- [ ] 每个控件选中后是否仍然知道它代表哪个字段？
- [ ] 是否有重置、取消、返回或撤销路径？
- [ ] 主要动作是否只有一个，危险动作是否明确后果？
- [ ] 状态是否同时有文字 / 图标 / 结构，是否区分了系统状态、模型状态和人工状态？
- [ ] 表格筛选、搜索、排序、分页是否靠近表格并能看见当前状态？
- [ ] 视频和快照是否保持比例、可读、可替代，错误是否有下一步？
- [ ] 键盘 Tab、Enter、Space、Escape 是否能完成核心流程？
- [ ] 焦点、对比度、目标尺寸、读屏名称是否符合第 7 节？
- [ ] 浅色、深色、窄屏和 200% 缩放是否都检查过？
- [ ] 规范是否通过公共组件和 token 实现，而不是页面内复制样式？

## 10. 针对当前项目的落地优先级

### P0：作为本规范确认后的硬门槛

- 继续使用 `LabeledSelect`，并将“选中值保留字段名 + 重置筛选”推广到所有无外置 Label 的横向筛选。
- 补齐 `success / warning / info / focus` 语义 token，并检查浅色 / 深色对比度。
- 统一事件处置状态、大模型状态、大模型判定和人工判定的显示层级。
- 所有空状态区分“无数据、无匹配、加载失败”，并给出对应下一步。
- 所有图标按钮补齐可访问名称；所有详情抽屉和模态框检查焦点回收。

### P1：提升值班效率和可信度

- 事件表增加明确的加载 skeleton、筛选摘要、数据更新时间和重试入口。
- 事件详情按“结论 → 证据 → 处置 → 历史”重排，降低用户来回寻找动作的成本。
- 表格支持排序、分页或明确的加载更多策略，并显示当前范围。
- 对摄像头异常、模型未配置、VLM 跳过和通知失败提供上下文内的可行动反馈。
- 增加浅色 / 深色 / 移动端的视觉回归截图和人工验收流程。

### P2：完善设计系统工程化

- 建立 `tokens.css` 或等价的语义 token 层，页面不再新增裸颜色。
- 为 Button、Select、Badge、DataTable、Dialog、Sheet、Toast 建立 Storybook 或组件示例页。
- 在 CI 中加入 TypeScript、组件测试、键盘路径和对比度检查。
- 为领域术语和状态名称建立唯一的标签源，禁止页面各自维护一份中文映射。
