# 解决方案包详情与体验产品方案

日期：2026-08-20

状态：已确认

范围：把现有“方案市场卡片 + 直接应用”升级为“浏览 → 了解 → 看效果 → 本机试跑 → 确认变更 → 应用 → 激活”的完整闭环。

## 1. 决策摘要

本期采用**独立详情页 + 页面内效果体验工作台 + 明确确认的应用流程**。

- 市场卡片负责发现与比较；点击卡片进入 `/marketplace/{pack_id}`。
- 详情页负责讲清楚业务价值、适用条件、摄像头部署、规则能力和应用影响。
- “效果演示”使用包内预渲染资产，打开即看、零推理、零副作用。
- “本机试跑”按用户明确操作启动，一次只运行一个场景，复用真实检测器但不写正式业务数据。
- “应用方案”前先展示变更清单；确认后才创建摄像头、视频副本和规则。
- 应用成功后建立可追踪的方案部署记录，并进入激活清单，引导替换真实源、校准区域、逐路启用和验证事件。

详情抽屉不作为主形态：它适合快速浏览，但不足以承载多机位视频、事件时间线、部署说明和试跑状态。独立“体验实验室”也不单独设一级入口，避免用户先理解一个新概念；实时试跑嵌入详情页，需要时展开。

本方案覆盖并替代 `2026-08-19-fastfood-pack-cameras-design.md` 中“不做方案详情页、不做详情路由、不在卡片播放预览”的阶段性非目标；原文关于双轨应用、停止态摄像头和不自动启动等约束继续有效。

### 1.1 形态比较

| 方案 | 优点 | 主要问题 | 决策 |
|---|---|---|---|
| 市场卡片 + 详情抽屉 | 改动小、返回列表快 | 多机位视频、部署说明和试跑状态过密，不适合分享与继续配置 | 不采用 |
| 独立详情页 + 预渲染演示 | 理解成本低、稳定、零资源占用 | 只能证明方案作者想表达的效果，不能验证本机链路 | 作为必备基础层 |
| 独立体验实验室 + 实时推理 | 验证能力强、可扩展 | 与方案理解割裂，入口和资源管理更重 | 不单独设入口 |
| 独立详情页 + 内嵌双层体验 | 同时满足理解、可信演示和本机验证 | 实现量最大，需要独立体验模块 | 采用 |

## 2. 背景与问题

当前方案市场已经能够展示包名、行业、版本、作者、描述、规则或摄像头清单，并可直接应用。但用户在应用前无法回答：

1. 这个方案解决什么业务问题？
2. 需要几路摄像头，分别装在哪里？
3. 每路会检测什么，触发时画面和事件是什么样？
4. 它能否在我的机器和画面上运行？
5. 点击应用后到底会创建或修改什么？
6. 应用后还需要做哪些工作才能真正上线？

现有快餐店包的 4 段 mp4 是检测链路占位源：灰底、区域线框、无真实目标和触发结果，编码为 OpenCV `mp4v`，也不保证浏览器可播放。它们不能直接承担产品层“效果演示”。

## 3. 产品目标

### 3.1 用户目标

- 门店负责人不理解算法名，也能判断方案是否解决自己的问题。
- 实施人员能明确机位数量、安装位置、画面要求和应用后的配置工作。
- 用户不应用、不创建正式资源，也能看到完整检测效果。
- 用户可以在本机用演示源或自己的已有画面试跑单个场景。
- 用户在产生副作用前看到准确的变更清单和风险提示。
- 应用后有连续的激活路径，不把用户丢在摄像头列表里。

### 3.2 产品目标

- 提升“进入详情 → 播放效果 → 完成本机试跑 → 应用”的转化。
- 降低因机位不匹配、规则区域未校准、误以为应用后自动运行而造成的失败。
- 为内置包、第三方已安装包和未来在线包提供同一套详情形态。
- 让方案作者通过稳定的包格式表达产品内容，不需要为每个包编写前端页面。

### 3.3 非目标

- 本期不建设在线支付、评分、评论、作者主页和商业授权。
- 本期不建设门店、机位角色、部署工单等新的业务实体；只增加轻量方案部署记录，用于资源归属、继续配置和状态恢复。
- 本期不做四路同时实时推理体验，不绕过全局推理锁。
- 本期不在体验中调用 VLM、发送通知或持久化正式事件。
- 本期不把用户摄像头画面上传平台或任何新外部服务。
- 本期不承诺演示效果等同于真实部署效果，页面必须明确“演示画面仅供理解能力”。

## 4. 用户与核心任务

| 用户 | 首要任务 | 决策信息 |
|---|---|---|
| 门店负责人 | 判断是否值得用 | 能解决什么、看起来是否有效、需要多少投入 |
| 实施人员 | 判断能否部署 | 机位位置、画面要求、规则参数、硬件与版本要求 |
| 运维人员 | 安全应用并上线 | 会创建什么、是否自动启动、后续校准和验证步骤 |
| 方案作者 | 交付可理解的包 | 结构化产品文案、预览资产、机位与规则映射 |

## 5. 产品结构

```mermaid
flowchart LR
    A["方案市场：发现与比较"] --> B["方案详情：理解价值与部署"]
    B --> C["效果演示：多机位预渲染"]
    C --> D["本机试跑：单场景实时推理"]
    B --> E["应用前变更预览"]
    D --> E
    E --> F["确认应用"]
    F --> G["激活清单：换源、校准、启动、验证"]
```

### 5.1 方案市场 `/marketplace`

市场页继续使用卡片网格，但卡片职责收窄为发现和比较。内部包格式无效或版本不兼容时不再静默消失：卡片保留可识别的名称/目录信息，标记“暂不可用”，详情说明原因并禁用体验和应用。

卡片展示：

- 封面或首个场景海报。
- 方案名、行业、版本、作者、来源。
- 一句话价值主张，而不是规则名堆叠。
- “N 路摄像头 / N 个检测场景”。
- “有演示”“可本机试跑”“需要选择已有摄像头”等状态。
- 主按钮“查看详情”；次按钮仅保留“快速应用”时也必须先打开变更确认，不再无解释直接应用。

### 5.2 方案详情 `/marketplace/{pack_id}`

沿用当前摄像头详情相同的客户端 catch-all + FastAPI SPA fallback：运行时安装的新包不需要在 `generateStaticParams()` 中枚举。前端路由只需识别 `path.startsWith("/marketplace/")`；验收必须覆盖开发端口和 8600 单端口的直接刷新、返回和复制链接。如果未来 Next 静态导出取消这条 fallback 能力，再降级为固定 `/marketplace/detail?id={pack_id}`，但不把查询参数作为首选产品 URL。

详情页由六个区域组成：

1. 概览 Hero。
2. 效果体验工作台。
3. 业务能力与检测结果。
4. 摄像头部署清单。
5. 运行要求与应用影响。
6. 说明文档与版本信息。

桌面端右侧有吸顶操作栏；移动端底部固定主操作按钮。

## 6. 详情信息设计

### 6.1 Hero 概览

必须展示：

- 方案名称与一句话价值主张。
- 行业、版本、作者、内置/已安装/在线来源。
- 摄像头数、检测场景数。
- 本机运行和数据边界说明。
- 当前兼容状态：可用、需要升级 open-cam、缺少模型、演示资产缺失。
- “体验方案”和“应用方案”两个动作。

兼容失败时详情仍可查看、效果演示仍可播放，但本机试跑和应用按钮禁用，并显示精确原因。

### 6.2 能解决什么

使用业务结果分组，不把 `zone_intrusion`、`zone_count` 等技术名作为主标题。

每项包含：

- 业务问题：例如“点餐区排队过长”。
- 系统动作：例如“区域内人数达到 5 人时打开待办”。
- 结果形态：客流记录、待办告警、趋势指标。
- 适用限制：遮挡、拍摄角度、夜间画质、只识别人形等。

产品文案不得超出当前模型与规则实际能力。例如“后厨闯入”只能表述为“有人进入设定区域”，不能写成“识别非工作人员”；除非包确实包含并启用了身份或工服识别模型。

规则技术类型作为次级信息，方便实施人员核对。

### 6.3 摄像头部署清单

新格式包按 `cameras[]` 展示；每路卡片包含：

- 机位名和用途。
- 建议安装位置、朝向、画面必须覆盖的区域。
- 示例海报。
- 该机位包含的检测场景和结果类型。
- 默认阈值、生效时段等关键参数摘要。
- 应用后是演示源还是需要用户选择现有源。

旧格式包没有机位拓扑时，显示“应用到一台已有摄像头”，并解释全部规则会挂到该摄像头；应用前必须选择目标摄像头。

### 6.4 应用影响

详情页必须使用人类可读的变更清单，不能只写“应用”。

快餐店示例：

- 新建 4 路停止态摄像头：门口、点餐、后厨、店内。
- 复制 4 段演示源到本机视频库。
- 新建 4 条规则并挂到对应摄像头。
- 不自动启动推理。
- 不覆盖、不去重已有摄像头和规则；重复应用会创建另一套。
- 换成真实源后需要按实际画面重新校准区域与计数线。

## 7. 效果体验设计

体验分为两层，两层含义必须在界面上区分。

### 7.1 第一层：效果演示

目标：任何用户打开详情都能立即看懂，不依赖本机模型、摄像头状态或推理性能。

形态：

- 每个场景提供 8–20 秒浏览器可播放的原始画面和预渲染结果，用户可同步切换“原始画面 / 检测效果”。
- 视频中包含真实或合成目标、检测框、目标类别/置信度、ROI/计数线、触发状态。
- 右侧同步展示事件样例：触发时间、事件标题、结果、是否需要处置。
- 用户可按机位切换、拖动进度、点击事件跳到对应时刻、重播。
- 无视频时回退到标注海报 + 文字步骤，不出现空白播放器。

预渲染视频是“产品演示资产”，与 `cameras[].source` 的“应用后检测源”分离。当前 `mp4v` 占位源可继续服务 OpenCV，但需要新增 H.264/yuv420p MP4 或兼容 WebM 的原始画面与效果资产。

页面固定文案：

> 这是方案自带的效果演示，用于说明检测逻辑；真实效果取决于机位、画质、模型和规则校准。

### 7.2 第二层：本机实时试跑

目标：让用户验证本机检测器能否跑通一个具体场景，而不是只看作者录好的结果。

入口：“在本机实时试跑这个场景”。打开前展示资源和数据说明：

- 一次只运行当前一个场景，最长 60 秒。
- 可选择“使用包内演示源”“使用一台已运行摄像头”“使用本机视频库”。
- 不创建正式摄像头、规则、视频或事件。
- 不保存快照，不调用 VLM，不发通知。
- 全部处理在本机；关闭页面、点击停止或超时后释放资源。

试跑画面展示：

- 实时视频或 MJPEG。
- 目标框、轨迹/计数线/区域。
- 当前人数、停留时长、进出方向等场景状态。
- 本次试跑命中时间线。
- 本机实际处理帧率和设备信息，避免用户把低帧率误认为规则失效。

试跑状态：`preparing / running / completed / stopped / expired / failed`。

资源约束：

- 全局最多一个主动试跑；已有试跑时返回明确的占用信息。
- 推理仍走全局 `_INFERENCE_LOCK`。
- 默认 60 秒，最多 5 分钟后强制清理会话。
- 浏览器断开不立即依赖客户端回收，后台 TTL 必须兜底。
- 包内 `trial_source` 必须含有当前模型可识别、能够走到声明规则结果的目标；现有灰底占位片在替换前只能用于效果说明，不能开放“本机试跑”。

### 7.3 体验与应用的边界

| 行为 | 效果演示 | 本机试跑 | 应用方案 |
|---|---|---|---|
| 使用推理模型 | 否 | 是，单场景 | 应用本身否，启动摄像头后是 |
| 写 SQLite | 否 | 否 | 是 |
| 创建摄像头/规则 | 否 | 否 | 是 |
| 保存事件/快照 | 否 | 否 | 正式运行后是 |
| 调用 VLM/通知 | 否 | 否 | 正式运行按配置 |
| 可重复退出 | 是 | 是 | 否，已创建资源保留 |

## 8. 应用与激活流程

### 8.1 应用前变更预览

点击“应用方案”后先请求服务端计算变更计划，展示：

- 将创建或影响的摄像头。
- 将创建的规则及所属机位。
- 将复制的视频资产。
- 不会执行的动作：不启动、不覆盖、不删除。
- 风险和后续人工步骤。

旧格式包在此选择目标摄像头；新格式包不出现目标摄像头选择。

变更计划携带包内容指纹。用户确认时回传指纹；如果包在确认期间被升级或替换，服务端返回 409，要求重新查看变更，避免“看到的”和“应用的”不是同一版本。

### 8.2 应用结果

成功后不只显示 toast，而是创建 `PackDeployment` 记录并展示结果摘要：

- 创建成功的摄像头与规则。
- 每路当前状态。
- “继续完成上线”主按钮。
- “返回详情”“查看摄像头”“查看规则”次级入口。

失败时按原子事务处理：数据库创建失败不留下半套摄像头或规则；已经复制的文件应回收，或在失败信息中明确可清理项。

### 8.3 激活清单

激活清单按摄像头逐路推进：

1. 选择真实 RTSP 或视频文件源。
2. 打开画面并确认视角。
3. 校准区域、计数线、阈值和生效时间。
4. 启动摄像头。
5. 运行一次验证并确认能看到预期事件或统计。

规则在应用后默认为“待校准”，不参与正式判断；用户完成对应机位校准后再明确启用。这样旧格式包应用到正在运行的摄像头时，也不会在未确认区域和阈值前立即产生事件。

`PackDeployment` 持久化当前进度，用户离开页面后仍能继续。它不是门店或工单领域模型，只记录一次方案应用与现有 Camera/Rule/Video 的归属关系。

建议表：

```text
pack_deployments
  id, pack_id, pack_version, pack_digest,
  status(configuring|active|degraded), created_at, updated_at

pack_deployment_resources
  deployment_id, camera_slot_id,
  kind(camera|rule|video), resource_id,
  ownership(created|bound), configured
```

删除或卸载方案包不级联删除已部署资源；资源缺失时部署状态变为 `degraded`。后续版本升级、回滚和“继续配置”都以部署记录为事实，不依赖摄像头名称猜测。

## 9. 方案包内容合同

### 9.1 原则

- 结构化字段是详情页的主数据源；`README.md` 是补充说明，不反向解析成产品字段。
- 老包通过规范化适配器生成可用详情；缺失内容显示降级态，不阻止查看和应用。
- 核心包合法性与展示资产合法性分层：核心规则错误时包不可用；单个预览损坏时该场景降级，不让整个包消失。
- 所有文件路径必须限制在包根目录内；Web 只看到资产 id，不看到本机绝对路径。

### 9.2 建议的 `pack.yaml`

## 10. 深模块与接口

详情与体验不应由前端直接拼 `pack.yaml`、README、规则 YAML 和文件路径。建立三个深模块，把复杂度收在稳定接口之后。

### 10.1 `PackCatalog` 模块

接口：

```python
list(filters) -> list[PackCard]
describe(pack_id) -> PackDetail
open_asset(pack_id, asset_id, range) -> AssetResponse
```

实现隐藏：

- 内置/已安装优先级与未来在线来源。
- 新旧 manifest 规范化。
- 规则参数的中文摘要。
- README 安全渲染数据。
- 资产 id 映射、路径限制、MIME 和 Range。
- 兼容性、预览可用性、试跑可用性计算。

不变量：同一个包版本的 `PackCard` 与 `PackDetail` 使用同一规范化结果；资产 id 只能访问该包声明且校验通过的文件。

### 10.2 `PackExperience` 模块

接口：

```python
start(pack_id, scene_id, source_ref) -> TrialSession
inspect(trial_id) -> TrialSnapshot
stop(trial_id) -> TrialResult
```

实现隐藏：

- 包内源、视频库和运行中摄像头三种输入适配。
- 临时采集、检测、跟踪、规则评估和可视化叠层。
- 全局推理锁、会话并发、TTL 和清理。
- 内存事件时间线与性能统计。
- 测试用 mock detector 和 in-memory frame source。

不变量：试跑不写 ORM 表、不存快照、不调用 VLM/通知；任意结束路径都可幂等 stop；会话过期后不能继续读取实时流。

### 10.3 `PackDeployment` 模块

接口：

```python
plan(pack_id, target) -> ApplyPlan
apply(pack_id, target, expected_fingerprint) -> ApplyResult
```

实现隐藏：

- 新包创建多路与旧包挂已有摄像头的双轨逻辑。
- 视频复制、名称去重、分辨率探测、坐标换算。
- 数据库事务和失败文件回收。
- 包内容指纹与确认时一致性检查。

现有 `apply_pack()` 迁入该模块实现，HTTP、CLI 和 Web 都只跨这一接口，避免三处各自判断新旧包。实现同时写入部署记录与资源映射；应用过程中创建的规则默认禁用，校准确认后才启用。

## 11. 依赖与接缝

| 依赖 | 分类 | 处理方式 |
|---|---|---|
| manifest 规范化、规则摘要、变更计划 | 进程内 | 纯逻辑，直接通过模块接口测试 |
| 包目录、预览媒体、SQLite | 本地可替换 | 测试使用 `tmp_path` 和临时 SQLite，不暴露额外外部接口 |
| 检测器、采集源 | 本地可替换 | `PackExperience` 内部接缝；生产使用 YOLO/文件/摄像头适配器，测试使用 mock/in-memory 适配器 |
| 在线市场平台 | 远程但自有 | 平台真正接入时定义目录端口；当前只有本地来源时不提前增加空抽象 |
| VLM | 真外部 | 不进入试跑；正式运行继续使用现有适配方式 |

## 12. HTTP 路由合同

### 12.1 详情与资产

```text
GET /api/packs/{pack_id}
GET /api/packs/{pack_id}/assets/{asset_id}
```

`GET detail` 返回 `PackDetail`，包含：

- 基础元数据和兼容状态。
- `presentation`、业务结果、运行要求。
- 规范化后的摄像头、场景、规则摘要。
- `experience` 能力与资产 URL。
- `application` 模式、影响摘要和可用状态。
- 安全处理后的说明文档。

资产路由支持 HTTP Range、正确 MIME、缓存 ETag；不接受任意相对路径。内置包可长期缓存，已安装包的 ETag 包含内容指纹。

### 12.2 试跑

```text
POST   /api/packs/{pack_id}/trials
GET    /api/pack-trials/{trial_id}
GET    /api/pack-trials/{trial_id}/live.mjpg
DELETE /api/pack-trials/{trial_id}
```

创建请求：

```json
{
  "scene_id": "door-flow",
  "source": { "kind": "bundled" }
}
```

`source.kind` 可为 `bundled`、`camera`、`video`；后两者分别要求 `camera_id`、`video_id`。运行中摄像头只复用当前帧，不替换或重启其采集线程。

错误语义：

| 场景 | HTTP | 文案 |
|---|---:|---|
| 包或场景不存在 | 404 | 方案包不存在 / 体验场景不存在 |
| 场景无试跑源 | 409 | 该场景仅提供效果演示 |
| 已有主动试跑 | 409 | 已有体验正在运行，请先停止后再试 |
| 检测器不可用 | 503 | 本机检测器暂不可用，仍可观看效果演示 |
| 源无可用画面 | 503 | 体验源无可用画面 |
| 会话过期 | 410 | 本次体验已结束，请重新开始 |

### 12.3 变更计划与应用

```text
POST /api/packs/{pack_id}/apply-plan
POST /api/packs/{pack_id}/apply
```

`apply-plan` 与 `apply` 使用相同 target 形状。`apply` 增加可选 `expected_fingerprint`；Web 必传，CLI 为兼容可省略并直接应用。

部署继续配置使用：

```text
GET   /api/pack-deployments/{deployment_id}
PATCH /api/pack-deployments/{deployment_id}/resources/{resource_id}
```

`PATCH` 只更新该资源的校准完成状态，并在规则确实存在、参数有效时启用规则；全部必要资源配置完成且至少一路摄像头运行后，部署状态可进入 `active`。

## 13. 前端状态与文案

### 13.1 关键按钮

- 卡片：`查看详情`
- 详情主动作：`体验方案`
- 详情次动作：`应用方案`
- 演示工作台：`重播演示`、`在本机实时试跑这个场景`
- 试跑：`开始 60 秒体验`、`停止体验`
- 变更确认：`确认创建这些摄像头和规则`
- 应用成功：`继续完成上线`

### 13.2 降级状态

- 无预览视频：展示海报和“该场景暂未提供视频演示”。
- 浏览器不支持编码：展示海报，并提供“下载演示视频”。
- 无 YOLO 模型或模型加载失败：预渲染演示照常，本机试跑禁用。
- 无现有摄像头：旧包仍可查看和演示，应用区域提示先去创建摄像头。
- 包版本不兼容：展示需要版本和当前版本，应用禁用。
- 第三方 Markdown 不安全：过滤 HTML、脚本、远程 iframe 和危险链接。

## 14. 安全与数据边界

- 体验默认只读取包内媒体；使用用户摄像头或视频必须由用户明确选择。
- 本机试跑不调用 VLM、不通知、不落事件和快照。
- 资产路由校验包根目录和声明白名单，拒绝 `..`、绝对路径和符号链接逃逸。
- 第三方 README 用允许列表清洗，不执行 HTML、脚本或自定义协议。
- 媒体设置合理的单文件和总包大小上限；在线包安装继续先下载到临时目录、完整校验后再替换。
- URL 安装必须限制协议、重定向次数、下载大小和超时，并拒绝访问环回、私网和本机文件地址；ZIP 解压拒绝路径穿越、符号链接、过多成员和解压炸弹。
- REST 响应不返回本机绝对源路径、prompt 原文或密钥。
- 包内 prompt 当前没有接入运行时复核链路，详情不得把它描述为“已启用的 AI 复核”；只有实际接线后才显示运行状态。
- 体验停止、过期、异常、服务关闭四条路径都释放采集与推理资源。

## 15. 可访问性与响应式

- 所有视频提供海报、文字说明和字幕/事件时间线，核心信息不依赖画面颜色。
- 播放、暂停、切场景和事件跳转可用键盘操作。
- ROI、目标框和触发态同时使用颜色、线型和文字标签。
- 移动端把视频、场景说明、机位卡改为单列；底部只固定一个主动作，避免遮挡内容。
- 用户开启减少动态效果时，不自动播放或循环预览。

## 16. 产品成功标准

产品层验收：

- 用户从任一方案卡片一击进入独立详情。
- 不点击应用即可切换所有机位并看到检测触发和结果说明。
- 用户能准确复述应用会创建什么、不会做什么、上线前还要做什么。
- 本机试跑结束后数据库摄像头、规则、事件、视频数量均不变。
- 应用必须经过变更预览；确认后返回完整结果和激活清单。

建议观察指标（默认不外传，可在本机开发日志或测试环境统计）：

- 详情打开率。
- 效果演示播放率、场景切换数。
- 本机试跑启动/完成/失败率及失败原因。
- 详情到应用确认的转化率。
- 应用后 24 小时内完成换源、校准和至少一路启动的比例。

## 18. 实施顺序

以下四个阶段共同组成首个完整版本，按依赖顺序交付，不把“体验”和“应用确认”留成无期限占位。

### 阶段 1：内容合同与详情模块

- 扩展 manifest；为四个内置包补齐结构化产品文案。
- 实现 `PackCatalog.describe/open_asset`、老包规范化和安全校验。
- 新增详情与资产 REST 路由，更新 OpenAPI 快照。
- 为快餐店制作浏览器可播放的真实/合成原始画面与检测效果资产，并替换为能触发本机试跑的匿名化/合成源。

### 阶段 2：市场与详情页

- 市场卡片改为“查看详情”主入口。
- 新增 `/marketplace/{pack_id}`、Hero、能力说明、机位清单、效果工作台。
- 完成媒体降级、移动端与可访问性。

### 阶段 3：本机试跑

- 实现 `PackExperience` 内存会话、单场景推理、叠层流和 TTL 清理。
- 接入包内源、视频库和运行中摄像头。
- 验证零持久化、零出站和全局推理锁。

### 阶段 4：应用确认与激活

- 深化现有 apply 为 `plan/apply` 接口，加入内容指纹和事务文件回收。
- 新增部署迁移与资源归属记录、变更确认、应用结果与可恢复激活清单。
- 更新 CLI、README、OpenAPI 与端到端测试。

未来在线市场接入时，复用同一 `PackCard/PackDetail` 合同；远程包可先展示平台元数据和预览，安装并完成本地校验后才允许本机试跑和应用。

## 19. 完整版本验收

以快餐店包为主路径：

1. 方案市场卡片显示“一体化快餐店方案、4 路摄像头、4 个场景、有演示”。
2. 点击进入详情，能理解门口、点餐、后厨、店内四个机位的目的与安装要求。
3. 切换四个场景，浏览器均能在原始画面与包含目标框、区域和触发结果的效果演示之间切换。
4. 对“点餐排队”启动 60 秒本机试跑，看到实际帧率、人数状态和命中时间线；停止后数据库和磁盘业务数据无新增。
5. 点击应用，先看到“创建 4 路停止态摄像头、4 条规则、4 个视频副本，不自动启动”的变更清单。
6. 确认后创建成功，规则保持待校准/禁用；结果页逐路列出资源，并引导换真实源、校准、启用、启动和验证。离开后可从部署记录继续。
7. 旧餐饮/零售/美发包也有详情和文字/海报降级体验；应用时仍必须选择一台已有摄像头。
8. 所有页面和接口使用中文用户文案；数据不出本机；全量测试通过。
